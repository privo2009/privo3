# UI 인계 규칙 — 지환 ↔ 희준

> 에셋이 만들어져서 게임 안에 들어가기까지의 절차 문서.
> 제작 규격 자체는 `docs/UI_ASSET_SPEC.md`, 화면 구성과 색·아이콘 원본은 `docs/UI.md`.

---

## 1. 역할 경계

| | 지환 (디자인) | 희준 (코드) |
|---|---|---|
| 만든다 | PNG, 3D 파트, 배치 명세 | — |
| 올린다 | — | 로블록스 업로드 |
| 붙인다 | — | 코드에 배치 |
| 관리한다 | — | 에셋 ID |

**지환은 Rojo / Git / VS Code를 쓰지 않는다.**
피그마와 Studio(Team Create) 둘만 사용한다.

에셋 ID(`rbxassetid://...`)는 희준이 전담한다. 지환이 ID를 다룰 일은 없다.

---

## 2. 경고 — 절대 하지 말 것

```
지환 PC의  C:\privo\privo3-assets  는 PNG 보관용 폴더다.
프로젝트가 아니다.
```

**이 폴더에 Rojo를 연결하면 Team Create의 스크립트가 전부 삭제된다.**

Rojo는 폴더 내용을 Studio에 "덮어쓰는" 도구다.
스크립트가 없는 폴더를 연결하면, Studio에 있던 스크립트를
"이 폴더에 없으니 지워야 할 것"으로 판단한다.

지환은 Rojo를 실행할 일이 없다. 실행하지 않으면 이 사고는 일어나지 않는다.

---

## 3. 배치 명세 템플릿

에셋만 넘기면 어디에 얼마나 크게 놓을지가 빠진다. PNG와 **함께** 아래 표를 넘긴다.

```
요소명 | AnchorPoint | Position(Scale) | Size(Scale) | 사용 에셋 | 비고
```

예시:

| 요소명 | AnchorPoint | Position(Scale) | Size(Scale) | 사용 에셋 | 비고 |
|---|---|---|---|---|---|
| 블럭스 보유량 | 0, 0 | 0.03, 0.05 | 0.18, 0.05 | icon_blox.png | 좌상단, 작게 |
| 힘 수치 | 0.5, 1 | 0.50, 0.97 | 0.30, 0.08 | icon_power.png | 하단 중앙, 특대 |
| 상점 버튼 | 0, 0 | 0.03, 0.20 | 0.08, 0.08 | icon_shop.png + tile_icon.png | 좌측 레일, 비율 고정 |

자리 배정 근거는 `docs/UI.md` "2. 세이프존" — 성장하는 값(힘)은 크게 아래,
쌓아두는 값(블럭스)은 작게 위. 메뉴는 좌측 레일, 판매는 우측·하단.
위 숫자는 형식 예시이고 실제 값은 G4 실측에서 확정한다.

### 모든 값은 Scale. Offset 사용 금지.

```
Scale  = 화면 크기의 비율 (0 ~ 1).  0.5 = 화면의 절반
Offset = 고정 픽셀 수
```

Offset을 쓰면 폰과 태블릿과 PC에서 크기가 제각각이 된다.
Scale만 쓰면 어느 화면에서든 같은 비율로 보인다.

`AnchorPoint`는 그 요소의 어느 지점을 Position에 맞출지다.
`0,0`=왼쪽 위 / `0.5,0.5`=한가운데 / `1,1`=오른쪽 아래.
화면 오른쪽에 붙는 요소는 AnchorPoint의 첫 값을 `1`로,
하단에 붙는 요소는 두 번째 값을 `1`로 둬야 잘리지 않는다.

### 정사각형이어야 하는 요소는 "비율 고정"이라고 적는다

Scale은 X가 화면 너비, Y가 화면 높이 기준이라 화면비가 바뀌면 정사각형이 찌그러진다.
아이콘 타일처럼 정사각형이 유지돼야 하는 요소는 비고란에 **"비율 고정"** 이라고 쓴다.
코드에서 `UIAspectRatioConstraint`를 건다. (`docs/UI.md` "5. 버튼 > 비율 고정이 필요한 요소")

## 4. 왕복 절차

```
1. 지환   PNG + 배치 명세표 작성
             ↓
2. 희준   로블록스 업로드 → 에셋 ID 발급 → 코드에 배치 → 커밋
             ↓
3. 지환   Studio(Team Create)에서 F5로 실행하여 눈으로 확인
             ↓
4. 지환   수정 요청 — 반드시 숫자로
             ↓
         (2번으로 돌아가 반복)
```

### 수정 요청은 숫자로

```
X  "버튼이 좀 큰 것 같아요"
O  "상점 버튼 Size를 0.10, 0.07 → 0.08, 0.06 으로"

X  "재화 칸이 너무 붙어있어요"
O  "블럭스 표시 Position Y를 0.10 → 0.12 로"
```

말로 된 요청은 왕복이 3~4번 늘어난다. 숫자면 1번에 끝난다.

## 5. 검증 관문 G1 ~ G4

**대량 제작 전에 반드시 통과할 것.**
미통과 상태로 만든 에셋은 규격 오류가 발견되는 순간 **전량 재작업**이 된다.
관문 1개는 파일 1~2장이면 되지만, 재작업은 20장이다.

관문은 각각 "몇 장으로 확인하는가 / 어떻게 확인하는가 / 무엇이면 통과인가"를 정한다.

---

### G1 — 버튼 9-slice
**Phase 6 착수 조건. 기한은 Phase 5 종료 전까지.**

```
조건   btn_yellow.png 1장
절차   업로드 후 3가지 크기로 동시에 화면에 띄운다
         (1) 작은 버튼  (2) 큰 버튼  (3) 가로로 아주 긴 버튼
통과   세 크기 모두 테두리 굵기가 같다
       세 크기 모두 모서리가 안 뭉개진다
실패   9-slice 24px 값을 재조정한다
       → 나머지 버튼 5종 착수 금지
```

이 관문이 가장 먼저인 이유: 24px 규칙이 틀렸다면 버튼 6종 + panel_frame이
전부 다시다. 1장으로 검증되는 것을 6장 만들고 확인할 이유가 없다.
(규격은 `UI_ASSET_SPEC.md` "1. 9-slice")

---

### G2 — 패널 2층 구조

```
조건   panel_frame.png + texture_lego.png
절차   두 크기의 창으로 띄운다
         작은 창  화면의 가로 60% x 세로 70%
         큰 창    화면의 가로 85% x 세로 85%
통과   두 크기에서 레고 무늬의 크기가 동일하다 (무늬가 같이 늘어나지 않는다)
       무늬 이음매가 보이지 않는다
```

무늬가 창 크기를 따라 커진다면 2층 구조가 깨진 것이다 —
테두리와 무늬가 한 장으로 합쳐져 있다는 뜻.
(규격은 `UI_ASSET_SPEC.md` "3. 패널 · 타일")

---

### G3 — 아이콘 실사용

```
조건   icon_power.png, icon_blox.png 2장
절차   HUD 실제 자리에 실제 표시 크기로 배치
         icon_blox  → 좌상단, 작게
         icon_power → 하단 중앙, 특대
       모바일 해상도에서 확인 (가장 작게 보이는 환경)
통과   둘의 실루엣이 구분된다 (40px 단색 상태에서도)
실패   → 나머지 타일 아이콘 14종 착수 금지
```

이 두 개를 고른 이유: 항상 화면에 떠 있는 재화 아이콘인데 **서로 떨어진 자리**에 있다
(`docs/UI.md` "2. 세이프존"). 나란히 있으면 비교로 구분되지만, 떨어져 있으면
각각 단독으로 읽혀야 해서 제약이 가장 세다. 여기서 통과하면 나머지 타일 아이콘 14종은 안전하다.
(형태 규칙은 `docs/UI.md` "7. 아이콘 > 그리는 규칙")

⚠️ **연필(`icon_edit`)에는 G3 통과가 적용되지 않는다.**
G3는 "타일 위에 얹힌 256짜리 아이콘이 타일 표시 크기에서 읽히는가"를 본다.
연필은 타일에 얹지 않고 표시 크기도 글자 높이라 검증 조건이 다르다
(`UI_ASSET_SPEC.md` "4-2. 인라인 아이콘").
연필과 `panel_value`는 둘 다 하단 띠에만 쓰이므로 **G4 더미 HUD에서 실제 크기로 확인한다.**
G3를 막지 않고, 관문을 새로 만들지도 않는다.

---

### G4 — 더미 HUD 통합

```
조건   G1 ~ G3 전부 통과 + 버튼 6종 완성
절차   하드코딩한 가짜 값으로 메인 HUD 전체를 배치해본다
       숫자는 반드시 최대 폭 문자열을 쓴다 →  999.99AB  (8자)
통과   세이프존 침범 없음 (기기 노치·홈바·로블록스 기본 UI에 안 가림)
       중앙 금지 구역에 화면 UI 없음 (캐릭터와 블록이 보여야 함)
       숫자 잘림 없음
```

`999.99AB` 8자를 쓰는 이유: 이 게임의 숫자는 가수 999.99 + 접미사 2글자가 최대 폭이다
(`DESIGN.md` "4. 숫자 표기", `docs/UI.md` "4. 글자 > 숫자가 UI 최대 제약").
개발 초반의 `1.00` 으로 맞춰놓으면 후반 유저 화면에서 전부 잘린다.
참고 게임 1이 정확히 여기서 무너졌다.

⚠️ **G4는 세이프존 구역 비율을 확정하는 관문이기도 하다.**
`docs/UI.md` "2. 세이프존 > 구역 비율"의 값(좌·우 20%, 상단 15%, 하단 25%)은
레퍼런스 기준 초안이며 G4 실측 후 확정한다.
확정 전까지 코드 쪽 `UiConfig.lua`는 만들지 않는다 — 두 번 고치게 된다.

## 6. 진행 순서

```
G1 → G2 → G3 → G4 → 대량 제작
```

UI 단계와의 대응 (`docs/UI.md` "UI Phase"):

```
U2  기초 에셋 (버튼 6종, 패널 2종, 텍스처, 아이콘 17종)  → G1 ~ G3
U3  더미 HUD                                            → G4
```

**관문은 희준의 코드 Phase와 무관하게 진행할 수 있다.**
지환은 Phase 4(성장) ~ Phase 5(드론) 완료를 기다리지 않는다.

G1~G4에 필요한 것은 "PNG를 화면에 띄워보는 것"뿐이고,
그건 게임 로직이 하나도 없어도 된다.
코드 Phase가 진행되는 동안 에셋 규격을 확정해두면,
Phase 6에서 붙이기만 하면 된다.

기한만 하나 지킨다 — **G1은 Phase 5 종료 전까지.**
